# Диагностика проблем

## Проверка доступности (ping) не работает или ведёт себя странно

Проверка доступности использует непривилегированный ICMP-сокет, а не «сырой» сокет —
доступ к нему регулируется настройкой ядра Linux `net.ipv4.ping_group_range`, а не
правами Docker-контейнера. Это настройка хоста (общая для всей системы, не
настраивается отдельно внутри контейнера). Проверить:

```bash
sysctl net.ipv4.ping_group_range
```

Если диапазон пустой или не включает пользователя, от которого запущен discovery (часто
выглядит как `1 0` — формально пустой диапазон), расширьте его на хосте (не в
контейнере):

```bash
sudo sysctl -w net.ipv4.ping_group_range="0 2147483647"
```

Большинство современных дистрибутивов Linux уже настроены разрешающе по умолчанию — это
стоит проверить в первую очередь, если именно проверка доступности ведёт себя не так, как
ожидается, а SNMP-опрос при этом работает нормально.

## Устройства не появляются после настройки дискaверинга

Частые причины:
- Неверная SNMP read-community.
- Устройство не отвечает на выбранной версии SNMP (v1/v2c/v3).
- Подсеть/маска в конфигурации дискaверинга указаны неверно.
- Расписание сканирования ещё не наступило.

Раздел **«Логи»** в дашборде показывает журнал процесса в реальном времени — там будут
видны попытки опроса и ошибки SNMP по каждому адресу.

## Сборка Docker-образа падает

Если вы устанавливаете через Docker и сборка образа завершается ошибкой — это почти
всегда локальная особенность окружения (нехватка места на диске, недоступность Docker Hub
из вашей сети), не проблема самого продукта. Проверьте свободное место на диске и
доступность `docker.com`/Docker Hub с вашего сервера.

Если проблема не решается — рассмотрите установку через [нативный пакет](installation.md)
(`.deb`/`.rpm`), которая не требует сборки образа вообще.

## Требуется лицензия / доступ заблокирован

Если после установки система внезапно перестала показывать данные и требует лицензию —
это, скорее всего, окончание бесплатного пробного периода (3 дня с первого запуска), не
сбой. См. [Лицензирование и пробный период](licensing.md) — что делать дальше.

## Дашборд открылся, но всё «только для чтения»

Это не сбой — так себя ведёт продукт, если у вас была именная (не пробная) лицензия и её
срок истёк: устройства продолжают опрашиваться, тревоги продолжают работать, но менять
настройки нельзя до продления. Свяжитесь с поставщиком за продлением.

## Ассистент отвечает ошибкой при отправке сообщения

Если ошибка явно говорит «ИИ-ассистент не настроен» — администратору нужно один раз
подключить провайдера на вкладке «ИИ-ассистент» в Настройках, см.
[Ассистент](features/ai-assistant.md#настройка-только-для-администратора).

Если провайдер настроен, но сообщения всё равно не проходят — скорее всего, сервер, на
котором работает discovery, не может достучаться до сервиса провайдера по сети (закрыт
исходящий трафик файрволом). Какой адрес проверять, зависит от выбранного провайдера:

**GigaChat:**
```bash
curl -v https://gigachat.devices.sberbank.ru/
curl -v https://ngw.devices.sberbank.ru:9443/
```
Оба адреса и оба порта (443 и нестандартный 9443) должны быть открыты для исходящих
соединений.

**OpenRouter:**
```bash
curl -v https://openrouter.ai/api/v1/chat/completions
```
Обычный порт 443, без каких-либо особых требований к сети — если GigaChat у вас работал, а
OpenRouter нет (или наоборот), проблема не в сети как таковой, а именно в доступности
конкретного адреса.

**Self-hosted (vLLM/Ollama/LM Studio/другой сервер):** адрес свой, проверяйте именно то
значение, что указано в поле «Base URL» настроек провайдера — например:
```bash
curl -v http://localhost:11434/v1/chat/completions
```
Убедитесь, что сервер вообще запущен и слушает указанный порт, а если он находится не на
том же сервере, где работает discovery — что сетевой путь между ними открыт (в том числе
если discovery запущен в Docker — сервер с моделью должен быть доступен именно из
контейнера, `localhost` внутри контейнера — это сам контейнер, не хост-машина). Если у
вашего сервера настроена авторизация, а поле «API-ключ» оставлено пустым — сервер обычно
отвечает `401`/`403`, не таймаутом.

Если запрос зависает/обрывается по таймауту — это сетевое ограничение на уровне вашей
инфраструктуры (файрвол, прокси), не проблема discovery. Если запрос проходит, но
discovery всё равно отвечает ошибкой — проверьте сам ключ/модель в настройках провайдера
(неверный API-ключ или несуществующее имя модели вернутся как ошибка уже на уровне
API провайдера, не сети).

## Ничего из этого не помогло

Свяжитесь с поставщиком напрямую — опишите, что видите на экране (лучше со скриншотом) и
что уже пробовали.
